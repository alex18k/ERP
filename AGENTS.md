# AGENTS.md

ERP生产管理系统 (MRP-driven manufacturing ERP). Monorepo, two apps at repo root: `server/` (Node + Express 5 + Prisma 5) and `client/` (Vue 3 + Vite 8 + Element Plus). UI/docs/conversation language is Chinese (订单/物料/排产/报工). Requirements: `erp.md` (root), `docs/ERP系统设计说明.md`, `docs/ERP项目开发计划.md`; living docs `docs/MRP运算逻辑.md`, `docs/生产订单取消逻辑.md`; UI/style guide `docs/erp-ui-instruction.md`. Git repo; `main` is the integration branch.

## Run / verify

```bash
# backend (port 3000) — ALWAYS tsx
cd server && npm run dev            # tsx watch src/index.ts

# frontend (port 63130, vite proxies /api -> localhost:3000)
cd client && npm run dev            # vite

# typecheck + build (MUST use these; npx vite build skips vue-tsc)
cd client && npm run build          # vue-tsc -b && vite build (strict noUnusedLocals)
cd server && npm run build          # tsc
```

- **No automated test suite.** Verify backend with `curl localhost:3000/api/...` + Bearer token. Login `POST /api/v1/auth/login {username,password}`; seed accounts `admin`/`sales01`/`user01`/`purch01`/`wh01`/`plan01`, all `admin123`.
- Node **22.12+** required (Vite 8).

## Gotchas (hard-won)

- Health check is only `GET /api/health` (before auth). Unknown `/api/v1/*` returns `code: 500 "接口不存在"` — not a crash.
- **Prisma pinned `5.22.0` — never upgrade** (v7+ contract CLI broke this project; `prisma.config.ts` removed).
- **`npm start` / `node dist/index.js` is broken**: `tsc` emits ESM with extensionless imports → `ERR_UNSUPPORTED_DIR_IMPORT`. Server is `"type": "module"`; only `tsx` runs it.
- **`MrpRun` has NO `createdAt`** (use `startedAt`/`completedAt`); `orderBy: { createdAt }` throws at typecheck AND runtime.
- Database is **PostgreSQL** (local apt service, db `erp`, user `erp`/`erp123456`, `DATABASE_URL` in `server/.env`). If the server fails with connection refused → `sudo service postgresql start`.
- Migrations at `server/prisma/migrations/<ts>_name/migration.sql`; **`migrations/` only starts from the PostgreSQL baseline `20261014000000_init`** (generated from `schema.prisma`). Older timestamps you see quoted elsewhere (`20260914130000_drop_work_order`, `20261007120000_add_batch_management`, …) are **SQLite-era history archived in `server/prisma/migrations_legacy_sqlite/`** — reference only, never applied, and not present in `migrations/`. To change schema: edit `schema.prisma` → `npx prisma migrate dev --name <x>` → `npx prisma generate` → restart server (or hand-write SQL and `npx prisma migrate deploy`).
- Full reset (test env): drop/recreate the `erp` database → `npx prisma migrate deploy` → `npx prisma db seed` → import scripts (see Master-data import below). If a migration fails mid-`deploy`, reset (test env) or `npx prisma migrate resolve`.
- **Concurrency**: inventory counters use atomic `increment`/`decrement` with `gte` guards (never read-modify-write); order numbers retry on `P2002` (`server/src/utils/retry.ts`); MRP single-instance uses `pg_advisory_xact_lock` (`mrp.service.ts`). Keep new write paths on those patterns — PostgreSQL has multiple writers, unlike the old SQLite single-writer setup.
- After any schema change you MUST `npx prisma generate` **and restart the running server**, or new fields are invisible at runtime.
- The running server is often started as plain `tsx src/index.ts` (no watch) → it does not hot-reload; restart it. Restart pattern: `(setsid npx tsx src/index.ts > /tmp/log 2>&1 < /dev/null &)`. Do NOT `pkill -f "tsx src/index.ts"` in the same command line — it matches and kills the invoking shell; use `pkill -f "src/inde[x].ts"` in a separate command.
- **权限码的唯一来源是 `server/prisma/seed.ts` 的 `permissions[]`**；`requirePermission` 对 ADMIN 角色**直接放行**（不看权限表）。复用已有权限码不需要动 seed；新增权限码给非 ADMIN 角色用，必须改 seed 并重跑 `npx prisma db seed`，否则只有 admin 能用。
- **错误码约定**: service 里 `throw new Error("业务原因")` 即可；基础 CRUD 的 `makeController`（`base.controller.ts`）把 create/update/remove 的错误映射为 **400**、list/get 映射为 **500**；其它 controller 多为手写 try/catch；未捕获异常与未知 `/api/v1/*` 都走 `errorHandler`/`notFoundHandler` → `code: 500`。
- **表格横向滚动条修复依赖 `client/src/styles/global.css`**: `.el-table--fluid-height.el-table--scrollable-x { max-height: none !important }`（表格页用 `max-height` prop 时 root 会裁剪滚动条）与 `.el-table__body-wrapper .el-scrollbar { padding-bottom: 12px }`（给滚动条预留空间，避免遮住最后一行）。这两条不要当冗余删掉。
- `remark.md` (root) 的物料分类章节**已过时**：它写的 `raw/accessory/semi/finished` 早已收敛为 `purchase`/`manufacture`。别照抄。

## Architecture / conventions

- **API envelope** `{ code, message, data, timestamp }`, success `code: 200`. The axios interceptor returns the whole envelope → pages read `res.data` (`res.data.items`, `{total,page,pageSize,items}`).
- Backend `server/src/{config,utils,middleware,routes,controllers,services}`. Every route needs `requirePermission("module:action")` + a matching method in `client/src/api/index.ts`.
- Blank base-entity CRUD via `crudRoutes()` (`server/src/routes/base.routes.ts`), permission suffix `:view/:create/:edit/:delete`.
- `client/src/api/index.ts` paths mirror backend (`orderApi`→`/sales-orders`, `productionApi`→`/production/...`, `stockApi`→`/stocks`).
- Material dropdowns: use remote search `materialApi.options({keyword,limit})` (lightweight), NOT `materialApi.list({pageSize:1000})`. `materialApi.types()` returns 物料类别 = `MaterialCategory(status=1)` ∪ 物料已用 `materialType` 的并集（`GET /materials/types`）。**Never render a per-row `el-select` with a large option list (e.g. 200 suppliers × N rows) — it explodes the DOM; use `el-select-v2` or remote search + pagination.**
- **物料类别**: `Material.materialType`（字符串）的可选值走主数据 `MaterialCategory`（基础数据→物料类别维护 `/base/material-category`，API `/api/v1/material-categories`，权限 `material:view`/`material:edit`）。物料表单的类别下拉**只能选不能新建**；改名会级联更新引用该名称的物料，仍被物料引用的类别禁止删除。类别与"分类"是两个字段，别混。
- **分类 `Material.category` 只有 `purchase`/`manufacture` 两值**（标签映射 `client/src/utils/category.ts` 的 `materialCategoryLabel`）；`materialApi.options({category})` 用它过滤。
- **库位 `Material.location` 存的是 `Warehouse.code`**（如 `A01` 材料仓 / `B01` 创信贴片），不是 id：`warehouseIdByLocation(warehouses, location)`（`client/src/utils/location.ts`）把它解析成 warehouseId。物料表单的库位选项来自 `/warehouses`；`BASE_LOCATIONS` 只是若干页面用的静态兜底列表（A01/B01/C01/D01），新增仓库不必改它。
- **货位 `WarehouseBin`**（仓库下的存放位置，`warehouseId` FK + 仓库内唯一 `(warehouseId, code)`）：维护入口 系统管理→货位管理（`/base/bin`，API `/api/v1/warehouse-bins`，查看 `stock:view`／维护 `stock:edit`，后端 `warehouseBinService` 手写校验）。
- **货位管理开关 `Warehouse.binManaged`**（仓库维护表单,`el-switch`）：只有启用货位管理的仓库才能维护货位、其出入库**必须**指定货位；未启用则不允许传 `binId`。`warehouseBinService` 创建/更新货位前校验 `warehouse.binManaged`；`warehouseService` 关闭开关前校验该仓库无货位库存、删除仓库前校验无货位。货位下有库存/流水时禁止删除。
- **库存按 `(物料, 仓库, 货位)` 维度**：`Stock.binId`/`MaterialBatch.binId`/`StockRecord.binId` 均可空（`null` = 未启用货位的仓库）。唯一约束用 PG **`NULLS NOT DISTINCT`**：`Stock(materialId,warehouseId,binId)`、`MaterialBatch(materialId,warehouseId,binId,batchNo)`。**Prisma 的复合唯一 `where` 类型把可空字段当 `number`（不接受 null），所以库存/批号的 upsert 一律走 `stock.service.ts` 的 `addStock()` / `applyBatchIn()` 里的原始 `INSERT ... ON CONFLICT (...) DO UPDATE`（命中 NULLS NOT DISTINCT 唯一索引），不要改回 `tx.stock.upsert`**。
- 所有出入库入口统一先 `resolveBinId(tx, warehouse, binId)` 校验货位，再落 `Stock`/`MaterialBatch`/`StockRecord`：手工出入库（`stockIn`/`stockOut`）、采购收货（`receivePurchaseOrder` 的 `options.binId`）、生产领料（`issueBatchMaterials` 行内 `binId`）、生产入库（`receiveBatchProduct` 末参 `binId`）、销售发运（`shipOrderItems` 行内 `binId`；自动发货沿用所选库存行的 `binId`）、移库（`transferStock`）。`listStocks`/`listBatches` 支持 `binId` 过滤并返回 `bin`，`listStockRecords` 返回 `bin`。
- **移库** `POST /stocks/transfer`（权限 `stock:edit`，前端入口=库存事务记录页「移库」按钮）：把某物料数量从源(仓库+货位)移到目标(仓库+货位)，同一事务内先原子递减源 `Stock`（`gte` 守卫）+ `applyBatchOut` 扣源批次，再 `addStock`+`applyBatchIn` 入目标（沿用同一批号），写出**一出一入两条 `StockRecord`**（共用 `documentNo`，事务类型 `MOVE-OUT`/`MOVE-IN`，`seed.ts` 已含）。源/目标不能相同；批号管理物料或源货位有批次库存时移库必须指定批号；`fromBinId`/`toBinId` 的货位规则同其它出入库（启用货位的仓库必填、未启用禁止）。
- **计量单位换算**: `MaterialUnitConversion` (per `materialId+unit`, `conversionRate` = 1 转换单位 = N 基本单位, `Material.unit` 为基本单位) 由基础数据→计量单位维护 (`/base/unit-conversion`, 权限 `material:view`/`material:edit`, API `/api/v1/unit-conversions`) 维护。`materialApi.options` 与 `bomApi.productOptions` 的返回附带 `units[]`/`unitRates{}`。**业务单据行同时存录入数量+单位与换算后基本数量**: `PurchaseOrderItem`/`SalesOrderItem` 有 `conversionRate`(下单快照)/`baseQty`; 库存与 MRP 一律用基本单位 — 收货 (`purchase.receive`)、发运 (`shipOrderItems`/`shipOrder`)、生产领料/入库 (`issueBatchMaterials`/`receiveBatchProduct`)、手工出入库 (`stockIn`/`stockOut`) 均按 `utils/unit.ts` 的 `resolveUnitRate`+`toBaseQty` 折算; MRP 在途/需求用 `baseQty` 或 `(quantity-receivedQty)*conversionRate`。录入单位未维护换算关系时后端报 400。
- The purchase-order list flattens one row per detail line: order-level actions use `row.orderId` (not `row.id`).
- Some page routes differ from menu labels: 采购建议 is `/mrp/purchase-suggestion` (not `/mrp/suggestion`).

## Adding a page (3 places, import depth)

1. View `client/src/views/<module>/<name>/index.vue`
2. Route `client/src/router/index.ts` (path must match the directory)
3. Menu `client/src/layouts/MainLayout.vue` (`menuItems`)

Import `src/api` as `../../../api` from `views/<module>/<name>/`; `views/login|home/` are one level shallower → `../../api`. `client` tsconfig is strict (no unused imports/vars).

## Business flow

- Orders must be `confirmed`/`in_production` before MRP sees them.
- 销售订单明细 `SalesOrderItem.line`(行号)为**必填正整数**（`assertItemLines`，缺失/0 → 400）；`PUT /sales-orders/:id` 是**整单 `deleteMany` + 重建**，所以提交明细**必须带 `id`**（两个编辑入口 maintain 页 / 销售订单弹窗均已回填，且 maintain 页保存后会重新 `loadOrder` 刷新 id）。**已发运行保护**：`deliveredQty > 0` 的行禁止删除，数量也不得小于已发量（未带 id / id 过期即视为删除该行 → 有发货记录就 400）；保留的行会带过 `deliveredQty` 与原 `status`。仅整单 `shipped`/`cancelled` 才整体禁止编辑。
- MRP (`POST /mrp/calculate`, perm `mrp:run`) expands active BOMs, buckets demand by material `orderCycleDays`, deducts stock (active warehouses) + in-transit (**confirmed** purchase order items with **blank** `status`, remaining qty) + **在制量** (open `planned`/`in_progress` production orders minus already-received qty, per material; also offsets each product×sales-order production suggestion) + **已发料量** (`ProductionBatchMaterial.issuedQty` on non-cancelled batches of open production orders), adds safety stock (first bucket only) → shortages; `purchase` → purchase suggestions, `manufacture` 且该物料是子装配（`isSemiProduct`，即有激活 BOM）→ production suggestions (quantity = order demand − 该物料×订单 in-process − 成品/半成品现库存). **Each MRP run cancels ALL `pending` purchase suggestions**, and MRP-generated POs are `draft`. See `docs/MRP运算逻辑.md`.
- Safety-stock replenishment is **separate**: `POST /mrp/safety-stock-suggest` (perm `purchase:create`) creates purchase suggestions for purchase parts with `stock + inTransit < safetyStock` (skips ones already pending).
- Purchase: **`PurchaseOrder.status` has only 2 values: `draft`/`confirmed`** (no cancel/received at header level); **`PurchaseOrderItem.status` has only 3: 空白 `""` (active/receivable)/`closed`/`cancelled`** — receipt progress lives on `receivedQty`, and **only blank-status items are receivable and count as MRP in-transit**. **Only `confirmed` orders can be received and only `confirmed` orders count as MRP in-transit** (draft orders are not receivable and not in transit). create → `PUT /purchase/:id/confirm` (requires supplier + orderDate + expectedDate + buyer + items; perm `purchase:approve`) → `PUT /purchase/:id/receive` (stocks in; writes `RCT-PO` record; receipt unit price > 0 overwrites `material.cost`; rejects non-confirmed POs and `cancelled/closed` items; does NOT update item or header status). MRP orders need editing (dates/buyer/supplier) before they can be confirmed. Receiving list = `GET /purchase?receivable=true` = confirmed orders with blank-status items whose `receivedQty < quantity`. 采购单维护页与销售单同规则：明细 `line` 必填正整数；`PUT /purchase` 同样整单重建、必须带 `id`（保存后 `loadOrder` 刷新 id），`receivedQty > 0` 的行禁止勾选/删除、数量不得小于已收量；明细查询统一 `orderBy: { line: "asc" }`（销售单同）。
- Production: create order → `PUT /production/orders/:id/schedule` (requires `planner` + `releaseDate`; per-batch plan dates come from the batch rows; requires an **active process route** for the product) → **copies the standard route into `ProductionOrderRoute`/`ProductionOrderStep`** (once per order, like `ProductionBatchMaterial` does for BOM) → creates `ProductionBatch` rows (**one per batch, no WorkOrder**) + `ProductionBatchMaterial` from the product's active BOM. **Report against a batch**: `POST /production/batches/:id/report` (single) or `POST /production/batch-report` (`{productionOrderId, items:[{batchId, processStepId, quantity, ...}]}`); `processStepId` is **mandatory** and must be a `ProductionOrderStep` of that order. A batch auto-completes when the **last step** (max `sequence`) has cumulative reported qty ≥ `batch.quantity`; when all non-cancelled batches complete AND scheduled qty ≥ order qty → production order (and sales order) auto-complete.
- **`WorkOrder` + `ProcessRouteAssignment` do not exist** (dropped in SQLite-era migration `20260914130000_drop_work_order`, archived in `migrations_legacy_sqlite/`). No per-step work orders; the batch is the unit of execution. Station-oriented views (车间看板/甘特图/产能负荷/工位产出排行) were removed. `WorkReport` now has `batchId` (not `workOrderId`) + `processStepId` (bare Int = `ProductionOrderStep.id`, **NOT NULL**), so `listWorkReports`/`getProductionReport` map step names manually. `listWorkReports`/`getWorkReportStats` filter by `orderNo`/`batchNo`/`batchId` (no `workOrderNo`). Export is per batch (`batchExport`), and `updateProductionOrder` no longer rewrites any work-order qty.
- **Two route tables, don't confuse them**: `ProcessRoute`/`ProcessStep` = standard template (基础数据→工艺路线, only affects *future* schedules); `ProductionOrderRoute`/`ProductionOrderStep` = per-order copy (加工单工艺路线 page, editable only **after** scheduling). `GET /production/orders/:id/route` returns the copy with `isOrderLevel: true` (+ `sourceRoute`), else the standard route with `isOrderLevel: false` (frontend renders it read-only). Edit via `PUT /production/orders/:id/route` (header) and `PUT /production/orders/:id/route/steps` (diff: update/create/delete; deleting a step already referenced by a `WorkReport.processStepId` is rejected). Steps added only to the order route have `sourceStepId: null`.
- Batch material issue/receive live under 库存管理: `POST /production/batches/:id/issue` (out, `ISS-WO`) and `POST /production/batches/:id/receive` (in, `RCT-WO`).
- Stock is now per `(material, warehouse)` (the old `materialId @unique` was removed); `Material.stocks` is an array — aggregate across warehouses for "current stock".
- **批号管理 (`MaterialBatch`)**: per `(materialId, warehouseId, batchNo)` stock rows (SQLite-era migration `20261007120000_add_batch_management`; the PG baseline already contains the table). `GET /stocks` list items embed `batches: [{batchNo, quantity}]` (stock.service.ts groups them); issue/receive/receive-production/shipping accept `batchNo` and write batch-level stock. `Material.batchManaged` flags batch-tracked materials; 库存查询 page flattens one row per batch (`flatList` in views/inventory/query). Backfill after reset: `npx tsx prisma/backfill-batches.ts`. **批号管控规则**: 只要出入库录入了批号就写入/扣减 `MaterialBatch`——即非批号管理物料（`batchManaged=false`）若录入了批号，也同样走批号管控并记批次行，未录入批号则不记批次明细。`applyBatchIn`/`applyBatchOut`（`stock.service.ts`）：批号管理物料入库缺批号自动生成、出库必须指定批号并校验批次余量；非批号管理物料批号可选。手工库存事务页（`views/inventory/record`）批号字段对所有物料显示：出库从该物料×仓库现有批次下拉选择（批号管理物料出库必选），入库可选择/输入批号（批号管理物料留空自动生成）。`materialApi.options` 返回 `batchManaged`。
- **Master-data import scripts** (`server/prisma/import-*.ts`, run with `npx tsx prisma/import-<x>.ts`): read the CSV exports in `docs/` (`物料主文件.csv`/`BOM.csv`/`供应商文件.csv`/`客户文件.csv`/`事务类型文件.csv`/`库位文件.csv`). Idempotent (upsert/dedupe by code); order matters only for BOM (must run **after** materials). 库位 maps to `Warehouse` (`code=A01, name=材料仓`). Reliable way to rebuild the ~10.5k-material / ~1.2k-BOM dataset after a DB reset.
