# MRP 分层净算（父件库存/在途覆盖的需求不再展开下阶 BOM）

日期：2026-10-29
状态：已确认（方案 A + A1）

## 1. 背景与问题

实例：销售订单 `SO202610290001` 明细 `20221015004.1` ×4000（交货 2026-10-31）。
该成品库存 20000（启用仓合计）≥ 需求 4000 + 安全库存 50，检查行净需求为 0、无生产建议；
但 MRP 仍产生：

- 生产建议 1 条：`20221015004.1-TPP` ×4000（同名半成品子件，库存 0）；
- 采购建议 21 条：成品 BOM 的 9 个采购子件 + `-TPP` BOM 的 12 个采购子件（各 4000 的一部分）。

根因（代码：`server/src/services/mrp.service.ts`）：

- `runMrp` 在净算之前，按**销售订单毛需求**递归展开 BOM（`expandDemand`，:180-250，调用点 :276）；
- 库存/在途/在制/已发料/已取消的冲抵只在**每个物料自身**的净算里做（:492-530）；
- 因此父件库存不能拦截子件需求，属于毛需求爆炸，系统性放大建议量。
- `docs/MRP运算逻辑.md` §2/§4 记录的也是这一现状口径。

## 2. 目标 / 非目标

目标：

- 父件「库存 + 在途」覆盖掉的订单需求，**不再产生下阶（子件）需求**（本例应为本单 0 条生产建议、0 条本单采购需求）。
- 分层处理：每层先净算、再用净额展开下一层；多层 BOM 逐层生效。
- 检查表、短缺清单、生产建议的既有列与口径保持可读、可比。

非目标：

- 不改安全库存独立补货（`/mrp/safety-stock-suggest`）。
- 不引入 MRP 参数开关（直接替换算法）。
- 不改销售订单/采购/生产的业务规则与接口。

## 3. 方案（已选 A，安全库存按 A1）

### 3.1 分层处理

1. 需求种子：销售订单明细（成品，第 0 层）+ 手工生产订单（无销售订单、已排产）的领料单子件需求；
2. 对 BOM 允许的物料做拓扑排序（父件先于子件），逐层处理；
3. 每个物料：沿用现有净算（分桶、库存→在途→在制→已发料→已取消、安全库存只进最早桶），产出检查行/短缺；
4. **只用净额展开下一层**，并把子件需求累加到子件物料上，等它被处理时再净算。

### 3.2 展开基数（关键口径）

对每个需求行（物料×订单×需求日）：

```
展开量 = max( 该行毛需求 − 已分配库存 − 已分配在途 , 该行分摊的在制量 )
```

- **含库存与在途**：真实可用供给，覆盖部分不再采购/生产，也不再有下阶需求；
- **不含安全库存**（A1）：安全库存只体现在检查行净需求，不驱动建议与下阶需求；
- **在制用 max 保底**：已排产生产订单的未发子件仍需采购；其子件需求由该订单承担，
  因此展开量至少覆盖在制量（避免「成品有库存 + 有在制单」时漏买子件）；已发料/已取消仍在子件层冲抵；
- 子件需求日 = 父行需求日 − 父件生产提前期（`manufactureLeadTime ?? leadTime`），沿用现规则；
- 子件用量 = 展开量 × BOM 用量 × (1 + 损耗率)，计量单位折算沿用 `resolveUnitRate` 同口径。

### 3.3 手工生产订单

- 沿用现状：按 `ProductionOrderMaterial.requiredQty` 注入子件需求（`-cancelledQty`），不按 BOM 重新展开；
- 为避免与上阶展开重复，**有「无销售订单的手工生产订单」的物料不再被展开 BOM**（沿用现守卫语义，
  由按物料判断替代原来的按父单判断）。

### 3.4 不变的部分

- 净算/检查行/短缺清单字段与计算（含 `stockQuantity/inTransit/wipQuantity/issuedQuantity/cancelledQuantity`、安全库存最早桶）；
- 生产建议公式（订单需求 − 在制 − 手工在制 − 现库存），按订单行输出；
- 采购建议 = 采购件各桶净需求；每次运行取消全部 pending 采购建议；
- 单实例 `pg_advisory_xact_lock`、运行记录/检查行/建议落库结构。

## 4. 影响

- 有库存/在途的成品、半成品，其子件需求按缺口缩小 → 采购/生产建议相应减少；
- MRP 检查表中**子件的「毛需求」= 来自父件净额的下阶需求**（数值会变小，属预期）；
- 顶级成品自身的检查行不变；生产建议口径不变（本就扣现库存）；
- 父件既有在制单时，子件需求不低于在制量（保底规则）。

## 5. 验证计划

1. 基准：保留改造前 run 39 的结果（生产建议/采购建议/检查行）用于对比；
2. 复现用例：`SO202610290001` / `20221015004.1` ×4000、库存 20000 →
   改造后：本单不再产生 `-TPP` 生产建议、不再产生本单来源的采购建议；`-TPP` 需求仅来自 `20230318001` 的缺口 800（库存 9200 / 需求 10000）；
3. 回归：同数据重跑 MRP，逐物料对比生产建议/采购建议差异，确认差异都能用「库存/在途覆盖」解释；
4. 构建：`server npm run build`（tsc）+ 重启（tsx）+ 接口冒烟（MRP 运行、生产建议页、检查页、采购建议生成）；
5. 数据复位：验证脚本写入的测试数据（如需）按基准还原。

## 6. 风险与缓解

- 核心算法改动影响面大：用「改前/改后同数据对比 + 差异解释」验证，不做无解释的差异接受；
- 多父件共用子件：按物料聚合需求后统一净算，避免重复；
- BOM 循环：拓扑排序检测并抛错（沿用 `BOM存在循环引用` 语义）；
- 性能：一次性加载 BOM/物料缓存；按「种子物料可达集合」查库存/在途/在制，避免全表 IN。
